# Claude Telegram Bridge 0.14.20

- Fresh installs now find the Claude session. The SessionStart hook runs inside Claude Code and records the session in `~/.claude/state/claude-telegram-bridge-sessions.json`, but the bridge looked for that record in its own state directory, `~/.local/state/claude-telegram-bridge`. On macOS, where the fallback lookups do not apply, and on Linux in most cases, a Telegram prompt reached the terminal while its answer never came back to the phone. The bridge and `doctor` now read the hook's file by default. The same mismatch hid the bridge's turn-ownership file from the Telegram MCP reply guard hook; the bridge now writes it to `~/.claude/state/claude-telegram-bridge-egress.json`, where the hook reads it, so duplicate replies are blocked again while the bridge owns a turn. `CLB_SESSION_SIDECAR` and `CLB_EGRESS_SIDECAR` still move either file; set the same value in Claude Code's environment as well. An existing install picks this up when the bridge restarts after the upgrade (the in-app update button restarts it); setup does not need to run again.
- Setup copies the hooks from the installed package instead of downloading them from the repository's main branch, so the hooks always match the installed version and setup downloads nothing. A missing hook file stops setup with a reinstall hint.
- `doctor` checks the tmux socket and session named in `bridge.env` (`CLB_TMUX_BIN`, `CLB_TMUX_SOCKET`, `CLB_TMUX_SESSION`), the same values the bridge and `claude-tg` use, instead of always checking `default/claude`. The warning about a Claude session outside the bridge uses the same target.
- `setup --dry-run` also lists the service files setup would write (systemd user units on Linux, launch agents on macOS) and every existing file it would replace, with what happens to each one first.
- Service files written by setup now start with a `Managed by claude-telegram-bridge setup` line. When a unit or launch agent with the same name already exists and setup did not create it, non-interactive setup first saves a copy as `<name>.bak-<time>` in the bridge config folder, outside the service folder so launchd or systemd never loads it, and warns before replacing the file; interactive setup asks first and keeps the file if you decline. `uninstall` stops and removes only the service files setup created, including those written by earlier releases, and keeps every backup.
- README: on Ubuntu, Debian and WSL, install pipx with `sudo apt install pipx` and `pipx ensurepath`. `python3 -m pip install --user pipx` remains only for older distributions, because Ubuntu 24.04 and newer refuse it (PEP 668).

Validation: unit coverage for the session file `doctor` finds after a fresh setup and a SessionStart hook run, the bridge-env tmux target in `doctor`, hook copies from the package with the network blocked, the missing-hook failure, package-data parity for every hook, dry-run listings on Linux and macOS without writes, backup-then-replace of a foreign unit and launch agent, the interactive decline and accept paths, uninstall keeping a foreign unit and every backup while removing setup's own unit and an earlier release's unit, and the README pipx guidance; two public tests that run the packaged hooks against the bridge configured the way setup configures it (the bridge reads the file the SessionStart hook writes, and the reply guard hook denies while the bridge owns the turn); eight mutation probes, each undoing one of these changes; the public export with its undefined-global gate, module parity check and vocabulary gate; private-data and token scans compared against the previous public tree; release-notes lint; twine check; and an installed-wheel check in an isolated environment that runs `setup --like-author --dry-run` and `doctor` under a temporary home. Source bundle, wheel and source distribution are included.

This release is published on GitHub and PyPI. Upgrading changes no installed hook, service file or `bridge.env`.
